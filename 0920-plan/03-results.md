# 03. 결과

`01-problems.md` 에서 찾은 문제를 `02-plan.md` 의 다섯 흐름으로 고치고, 이어서 외장 모델과 남은 상태를 한 번 더 손봤다. 숫자는 개선 전 빌드와 최종 빌드를 같은 시간대에 번갈아 두 번씩 재서 얻은 중앙값이다(`0920-plan/perf/results/final-*.json`). 표본 여덟 개 모두 다른 브라우저가 GPU 를 쓰지 않는 조건(`foreignGpuPct` 0) 이다.

- 도시 준비 시간(readyMs) 은 6.0초와 6.1초로 차이가 없다.
- 조감 장면의 link 16개는 최종 빌드가 그 시간에 미리 컴파일을 돌리고 있기 때문이다. 조감은 여유가 있어 p95 가 오히려 줄었다.

### 충돌 판정

- `hitsBuilding` 을 `solidIndex.js` 로 옮겨 할당 없이 계산하고, 배열마다 48 단위 격자를 캐시하는 `hitsAnyBuilding` 을 도보, 차량, 비행, 헬기, 포탄, 원격 포탄, 조준선 미리보기 아홉 곳에 넣었다. 1000채 도시에서 같은 선분 3000개를 볼 때 전부 훑기보다 네 배 넘게 빠르다.
- `NearbyCreators` 의 가림 판정도 picking mesh 광선 대신 같은 격자를 쓴다. 광선 하나가 상자 1000개를 보던 4Hz 비용이 사라졌다.

### 도보와 산탄총

- 산탄총을 넣었다. 분당 70발, 탄창 6발, 여유탄 24발, pellet 9개, pellet 산포 0.16rad, 사거리 45, 차 한 대를 부수는 데 pellet 27발이다. pellet 세 발묶음이면 차가 터진다.
- pellet 은 결정적 해시로 퍼진다. 같은 발사는 어디서 보든 같은 탄착이다.
- 관형 탄창이라 한 발씩 0.5초에 넣고, 넣는 도중에 쏘면 장전이 끊긴다. 발마다 장전 소리가 난다.
- 펌프는 발사마다 뒤로 갔다 돌아오고 지지 손이 따라간다. 조준선은 pellet 산포 크기의 원이다. 단축키는 5다.
- 총 모델의 정적 조각을 묶어 뷰모델 draw call 을 줄였다.

## 검증

- 단위 테스트 604개 전부 통과. 작업 전부터 실패하던 `tier-buildings.test.mjs` 의 부품 예산(bronze 0 high 260개, 한도 220개) 도 이번에 닫았다. 옥상 에어컨의 폭 0.1 날개 세 장을 빼고(도시 전체에서 수백 개다) 상가 거리의 옥상 실외기를 한 집 걸러 하나로 줄여 212개가 됐다.
  - 차량 1000대 프레임 예산 테스트는 다른 작업과 CPU 를 같이 쓰면 3ms 를 넘겨 실패한다. 혼자 돌리면 통과한다.
- `npx eslint src/world src/routes/WorldPage.jsx` 오류 없음. 작업 전 `WorldScene.jsx` 에 있던 오류 세 개도 사라졌다.
- `npm run build` 통과.
- Playwright 브라우저 테스트(`npm run test:world`, 소프트웨어 GL) 는 개선 전 7개 실패 7개 통과, 개선 후 6개 실패 8개 통과다. 실패 여섯 개는 개선 전에도 실패하던 것이고(시간 초과, 갤러리 개수, WebGL 실패 처리, 남아 있는 TEMP 테스트), 제트 조종석 테스트 하나는 개선 후에 통과로 바뀌었다.
- 지상 차량 네 대를 차례로 타는 테스트는 양쪽 모두 90초 상한에 걸린다. 개선 후에는 네 번째 차량의 조준경 확인까지 진행한 뒤 걸리므로 개선 전보다 멀리 간다. 그 조준경 표시(1배에서 V 로 2배) 는 따로 돌려 통과를 확인했다.
- 작업 중 회귀가 하나 생겼다가 고쳤다. 비행 중 제작자 카드가 마운트된 다음 프레임에야 투명도를 받아 그 사이에 읽으면 0 이었다. 카드가 붙는 순간 투명도를 넣도록 고쳤고 세 번 연속 통과를 확인했다.
- 화면 확인: 조감 주간과 야간, 도보 권총과 산탄총(사격, 재장전, 정조준), 차량 3인칭과 1인칭(거울 셋, 바늘 계기, 계기 화면), 야간 전투기 실내(HUD, 계기 화면, 활주로 등), 세단 조향, 오토바이 코너링, 프로펠러기 스로틀, 폭격기, 야간 SUV 등화와 전투기 애프터버너, 전투 차량 넷의 차체와 포탑을 찍어 이전 빌드와 비교했다. 콘솔 오류와 WebGL 경고는 없다.

## 코드 리뷰에서 고친 것

전체 변경을 따로 리뷰해 다음을 고쳤다.

| 문제 | 증상 | 고친 방법 |
|---|---|---|
| `Blast` 가 목록에서 빠진 폭발의 나이를 0 으로 읽음 | 폭발이 사라지기 직전 한 프레임 동안 섬광이 다시 번쩍인다 | 없으면 null 을 돌려주고 마지막 모습 그대로 둔다. `Projectiles` 와 같은 규약이다 |
| 그림자 caster 가 빈 shape 도 갱신 구간을 등록 | WebGL2 의 bufferSubData 는 길이 0 을 "나머지 전부" 로 읽어 버퍼 전체가 올라간다 | caster 가 하나도 없으면 올리지 않는다 |
| 쓰러진 뒤 관형 탄창 장전 소리 한 번 | 상태가 새로 만들어져 장전 횟수가 0 으로 돌아가는데 소리 조건이 "달라지면" 이었다 | 횟수가 늘어났을 때만 울린다 |
| 실내 계기가 공유 geometry 를 해제 | `ShaderPrewarm` 이 실내를 띄웠다 내릴 때마다 공유 geometry 의 GPU 버퍼가 풀린다 | 계기 mesh 에 `dispose={null}` 을 단다 |

리뷰가 확인하고 문제 없다고 본 것은 교통의 순수성과 겹침, picking 상자의 raycast, `gl.shadowMap.render` 되돌리기, `StaticBatch` 의 해제 범위, 산탄총 피해 집계, 멀티플레이 pose 전송 경로다.

## 시도했다가 되돌린 것

- 총구 섬광과 손전등 조명을 끄지 않고 세기만 0 으로 두는 방법을 넣어 봤다(`perf/results/flash-*.json`). 광원 개수가 변하지 않아 첫 발의 셰이더 재컴파일(link 14개) 은 사라졌지만, 도보 정지가 114fps 에서 99.6fps 로 13% 느려졌다. 조명 하나가 모든 화소에서 계산되기 때문이다. 일회성 멈춤보다 상시 비용이 커서 되돌렸다. 대신 `ShaderPrewarm` 의 시작을 2초에서 1.2초로 당기고, 탈것을 고른 뒤 카운트다운 동안에도 도시 조명 조합만은 미리 만들게 했다. 이 쪽은 도보 사격의 셰이더 link 를 19개에서 13.5개로 줄이고 p95 를 75ms 에서 65ms 로 낮췄다(`perf/results/prewarm-*.json`). 탈것 진입이 늦어지지 않는지는 브라우저 테스트로 확인했다.

## 주행 중 끊김을 따로 잡은 것

위 표는 6초 표본이다. 20초를 달리면 같은 빌드가 p95 173ms 에 20초에 긴 프레임 144회로 전혀 다른 그림을 보였다. 6초 표본이 해상도 자동 조절의 warmup 4초와 겹쳐 정책이 거의 작동하지 않은 구간만 재고 있었다.

원인은 셋이다.

| 항목 | 기존 | 변경 |
|---|---|---|
| Canvas 의 dpr 주인 | `dpr={[1, 등급값]}` 이라 R3F 가 다시 렌더될 때마다 낮춘 해상도를 되돌렸다. 되돌림마다 `gl.setSize` 가 드로잉 버퍼를 다시 잡는다 | `dpr={null}` 로 R3F 를 빼고 `onCreated` 가 첫 값을 정한다. 주인은 `AdaptiveResolution` 하나다 |
| 내림 판정 | 1초 지수 이동 평균이 임계값 22ms 한가운데에 머물러 2초마다 오르내렸다 | 최근 3초에서 33ms 를 넘긴 프레임의 비율로 본다. 35% 가 2.5초 이어져야 내리고 쿨다운 8초, 세션당 3회, 바닥은 등급값의 0.75배다 |
| 헛된 내림 | 화소가 아니라 CPU 에 묶인 장면에서도 끝까지 내려가 화면만 흐려졌다 | 내린 뒤 3초의 비율이 나아지지 않으면 직전 값으로 되돌리고 그 세션에서는 고정한다 |
| 1인칭 거울 | 3프레임마다 도시를 한 번 더 그렸고 그림자 caster 재구성과 같은 프레임에 겹쳤다 | 4프레임마다 그리고, 거울 프레임이 아닌 번호에서만 caster 를 다시 채운다. 거울 패스 동안 도시 상세를 먼 단계로 내린다 |
| 매 프레임 할당 | `trafficBoxes` 가 프레임마다 차 객체 수백 개와 배열 셋을 새로 만들었다 | `fillTrafficNear` 가 객체와 배열을 다시 쓴다. 반경 판정과 파괴 판정을 한 루프에서 끝낸다 |
| 주행 중 라벨 | 제작자 라벨 여섯 개가 매 프레임 DOM 에 transform 을 쓰고 후보를 0.25초마다 다시 골랐다 | 주행 중에는 셋으로 줄이고 0.5초마다 고른다. 후보 가림 판정도 광선 대신 충돌 격자를 쓴다 |

20초 주행을 번갈아 두 번씩 잰 결과다. 캔버스 해상도 변경 횟수가 20초에 7회와 11회에서 2회와 3회로 줄었다.

| 장면 | fps 전 | fps 후 | p50 전 | p50 후 | p95 전 | p95 후 | p99 전 | p99 후 |
|---|---|---|---|---|---|---|---|---|
| 차량 3인칭 20초 | 16.1 | 18.8 | 32.1ms | 26.6ms | 340ms | 197ms | 823ms | 416ms |
| 차량 1인칭 20초 | 16.4 | 18.9 | 30.5ms | 19.1ms | 300ms | 264ms | 477ms | 388ms |

이 표의 절대값은 위 6초 표는 물론 서로와도 비교하면 안 된다. 측정 시점에 데스크톱 Chrome, gitkraken, postgres, docker 가 같이 돌아 load average 가 4였다. 같은 조건에서 개선 전 최종 빌드(`dist-final3`) 를 다시 재니 3인칭 주행이 71fps 가 아니라 25fps 로 나왔다. 기계 상태가 세 배를 가른다. 번갈아 잰 두 열의 차이만 읽을 수 있다.

36초를 이어서 달리며 3초 구간마다 나눠 보니 fps 가 22에서 26 사이를 오갈 뿐 시간이 갈수록 무너지지는 않았다. 메모리 증가나 누적 상태 때문이 아니다.

## 남은 문제

- 교차로에 신호나 양보가 없다. 감속만 하므로 다른 경로의 차끼리 교차로 한가운데서 겹칠 수 있다.
- AI 차량의 유턴은 경로 끝 조금 앞 도로 한가운데서 한다. T 자 끝에서도 같다.
- 도시별 차선 표를 처음 만들 때 32ms 가 한 번 든다. 지금은 한가할 때 미리 만들지만 그 순간이 겹치면 한 프레임이 길어질 수 있다.
- 도보 이동과 사격 장면의 p95 는 136ms 로 여전히 길다. 미리 컴파일이 끝나기 전에 쏘면 총구 섬광 조명 조합이 그 자리에서 만들어진다. 조명을 상시로 두는 방법은 아래처럼 재 보고 되돌렸다.
- 1인칭 실내의 draw call 은 실측이 아니라 구성으로만 줄였다. 실내만 따로 재는 측정은 없다.
- `world.spec.js` 의 기존 실패 여섯 개는 이번 작업 범위 밖이라 그대로 둔다.
- 밤낮을 바꾸는 순간 가로등과 실내등이 생겼다 사라져 조명 개수가 바뀐다. 그때 한 번은 셰이더가 다시 만들어진다. 밤 안에서는 가로등 개수를 고정해 두어 더는 바뀌지 않지만, 전환 한 번은 남는다. 미리 컴파일이 반대쪽 시간대 조합까지 덮게 하면 없앨 수 있다.
- 주행 중 긴 프레임은 줄었지만 없어지지 않았다. 지금 기계 상태에서는 개선 전 빌드와 개선 후 빌드 모두 3초마다 긴 프레임이 20회 넘게 나온다. 조용한 기계에서 다시 재야 남은 몫이 코드인지 기계인지 갈린다.
- 해상도 자동 조절은 세션당 3회까지만 바꾼다. 세 번을 다 쓰고 나면 그 뒤로는 장면이 아무리 무거워져도 해상도를 더 내리지 않는다. 잦은 전환이 주는 멈춤보다 낫다고 보고 고른 값이다.
