# 01. 문제점

2026-09-20 에 오픈월드(`/world`) 를 측정하고 코드를 읽어 찾은 문제다. 측정 환경과 방법을 먼저 적고, 문제를 영역별로 나눈다. 숫자는 모두 `0920-plan/perf/results/*.json` 에 남아 있다.

## 측정 환경과 방법

- 기기는 AMD Radeon 780M(Phoenix1, 통합 GPU), CPU 16 스레드, 메모리 14GB 다. 제작자 1000명 도시, 화면 1440x900, 품질 medium 이다.
- 브라우저는 headless Chromium 에 ANGLE GL 백엔드를 붙였다. renderer 문자열이 `ANGLE (AMD, AMD Radeon 780M Graphics (radeonsi phoenix ACO), OpenGL ES 3.2)` 라서 실제 GPU 로 그린다.
- vsync 와 프레임 상한을 풀었다. 60Hz 에 묶이면 개선 전후 차이가 보이지 않는다.
- 측정 하네스는 `0920-plan/perf/world-perf.spec.js` 다. 장면마다 fps, 프레임 시간 분위수, rAF 콜백 안의 JS 시간, draw call, 삼각형, 셰이더 link 수, React commit 수, CPU profile 상위 함수를 뽑는다. 함수 이름이 보이도록 minify 를 끈 production 빌드로 잰다.
- 외부 GPU 경쟁이 있을 때는 같은 조건을 다시 재도 fps 가 6에서 9 사이로 흔들렸다. 그래서 실험에서는 30% 넘는 차이만 원인으로 본다.

조감은 여유가 있지만 지상 시점은 p95 가 66~238ms 다. 평균 fps 보다 이 긴 프레임이 체감 렉이다. 도보에서 쏘기 시작하면 21fps 로 떨어지고, 차량은 3인칭부터 25fps 다.

### 처음 측정이 틀렸던 이유

처음 잰 값(`perf/results/baseline.json`) 은 도보 정지 4.1fps, 차량 3인칭 2.7fps 였다. 같은 빌드를 한 시간 뒤 다시 재니 54.4fps 와 25.1fps 가 나왔다. 사용자 데스크톱 Chrome 이 01:12 부터 떠 있었고, 그 GPU 프로세스가 CPU 43%, renderer 가 65% 를 쓰고 있었다. 열어 둔 3D 탭과 GPU 를 나눠 쓴 것이다. 이 뒤로 하네스는 다른 브라우저 GPU 프로세스의 CPU 시간을 `foreignGpuPct` 로 함께 남기고, 값이 높은 표본은 버린다.

이 오염 자체도 문제를 드러낸다. GPU 를 다른 탭과 나눠 쓰는 흔한 사용 환경에서는 draw call 과 화소 비용이 열 배 넘게 부풀어 도시가 멈춘 것처럼 보인다. 해상도를 자동으로 낮추는 안전망이 필요한 이유다.

## A. 지상 시점 렌더링 비용

- 외부 GPU 경쟁이 있던 1차 측정에서 화면을 800x500(화소 31%) 으로 줄이면 도보 정지가 4.1 에서 16.6fps 로 올랐다. GPU 가 밀릴 때는 비용이 화소 수를 따라간다.
- `logarithmicDepthBuffer` 를 끄면 조감은 47.4 에서 59.8fps 로 올랐지만 도보는 4.1 과 4.0 으로 같았다(1차 측정). 로그 깊이의 early-Z 손실은 조감에서 25% 쯤이다. 도로 층 사이의 깊이 싸움을 막으려고 넣은 것이라 이번에는 그대로 둔다.
- 품질 low(그림자 없음, 차량 200대, 삼각형 1.68M) 에서도 도보는 6.4fps 였다(1차 측정). 삼각형 수는 주원인이 아니다.
- 구성요소를 하나씩 끈 1차 실험(`perf/results/off-*.json`) 에서 건물 타일 전체를 꺼도(삼각형 4.25M 에서 2.49M) fps 는 잡음 안에서만 움직였다. 반면 하늘, 바다, AI 항공기, 공항, 가로등을 함께 끄자 draw call 이 555 에서 268 로 줄고 fps 가 8.9 에서 14.8 로 뛰었다. 삼각형은 그대로였다.
- 경쟁이 없는 2차 실험(`perf/results/off2-*.json`) 도 같은 방향이다. 기준 50.9fps 에서 공항과 AI 항공기를 끄면(draw 555 에서 285) 68.6fps, 그림자까지 끄면(draw 221) 87.2fps 다. 하늘과 바다만 끄면 draw 가 17개만 줄어도 62fps 라 화면 전체를 덮는 셰이더 비용도 있다. picking 상자만 끄면 55.1fps, 투명 재질을 모두 끄면 56.9fps 로 작은 몫이다.
- 그림자 하나만 끄면 draw call 이 555 에서 365 로, 삼각형이 4.25M 에서 2.65M 으로 준다. 그림자 패스가 draw 190개와 삼각형 1.6M 을 쓴다. 지상에서는 `grounded` 가 켜져 타일로 나누지 않은 `landscape` 배치(도시 전체의 나무, 가로시설, 지형) 가 통째로 그림자를 던지기 때문이다.
- draw call 을 많이 쓰는 곳은 공항 두 곳 180개, AI 항공기 90개, 1인칭 총 모델 59개다. 공항과 항공기는 상자 mesh 를 조각마다 따로 그린다.
- 제작자마다 둔 picking 상자(`materials.pick`) 는 `opacity 0`, `colorWrite false` 라 보이지 않지만 PBR 셰이더는 그대로 돈다. 2차 실험에서 이 상자만 끄면 50.9 에서 55.1fps 가 됐다.

## B. 셰이더 컴파일 멈춤

- 도보에서 처음 쏠 때 셰이더 프로그램 22개, 차량에서 1인칭으로 바꿀 때 80개가 새로 link 된다. 그 6초 표본에서 CPU 시간의 9~32% 가 `getProgramInfoLog` 로, 동기 컴파일을 기다린 시간이다.
- `renderer.debug.checkShaderErrors` 가 기본값 true 라 production 에서도 link 마다 로그를 동기로 읽는다.
- 밤에는 `StreetLamps` 가 0.3초마다 가까운 가로등 pointLight 목록을 새로 만든다. 조명 개수는 three.js 프로그램 캐시 키라서, 개수가 바뀌는 순간 도시 전체 재질이 다시 컴파일된다.
- 도보 손전등(spotLight) 도 처음 켤 때 조명 개수가 바뀌어 같은 일이 한 번 일어난다.

## C. React 재렌더

- `WorldPage` 가 탈것 상태를 0.12~0.15초마다 `setRideStatus` 로 올린다. `WorldScene` 은 memo 되지 않았고 `onExplore` 에 인라인 함수가 넘어가므로, 도시 전체 R3F 트리가 초당 7~8번 재조정된다. 도보 정지 6초에 react-dom commit 235번, R3F commit 109번이 찍혔다.
- `CarMode` 는 포탄과 폭발을 0.04초마다 `setOrdnance` 로 올리고, 1인칭이면 `setCockpitStatus`, `setWheels`, `setAimView` 도 부른다. 실내 전체가 25Hz 로 재조정된다.
- `FlightMode` 는 발사체와 폭발을 매 프레임 `setLive` 로 올린다. `WalkMode` 의 `Blasts`, `AirTraffic` 의 `Wrecks` 도 살아 있는 이펙트가 있으면 매 프레임 setState 를 부른다.

## D. AI 차량

- `TrafficCars` 렌더, `WalkMode` 위협 판정, `CarMode` 충돌 판정, `FlightMode` 지상 공격이 한 프레임에 각자 차량 전체를 다시 계산한다. 도보에서는 사격 중 한 번 더 한다. 단위 테스트 전체를 병렬로 돌릴 때 `trafficPose` 1000번이 8.7ms 로 찍혀 예산 테스트가 실패했지만, 따로 재면 0.1ms 안팎이다. 브라우저 profile 에서도 `trafficPose` 는 CPU 의 1% 남짓이다. 계산 비용보다 아래의 동작 문제가 더 크다.
- 경로 20개에 차를 `index % 20` 으로 똑같이 나눈다. 길이 138 인 공항로와 12303 인 순환로가 같은 수의 차를 받아 짧은 길은 차가 겹쳐 쌓인다.
- 속도가 경로 길이의 비율(`progress/초`) 로 정해진다. 짧은 경로의 차는 초당 0.3 단위로 기어가고 긴 경로의 차는 빠르다.
- 같은 차선의 차가 서로 다른 속도로 달려 서로를 뚫고 지나간다.
- 열린 경로 끝에서 진행률을 `mod 1` 로 감아 차가 경로 시작점으로 순간이동한다.
- 교차로와 급커브에서 속도가 줄지 않는다. 브레이크등은 곡률 표만 보고 켜지고 실제 감속과 관계가 없다.
- 렌더러는 차 한 대마다 `Object3D.updateMatrix` 를 14번 부르고, 매 프레임 instance 버퍼 전체를 올린다.

## E. 충돌 판정

- `hitsBuilding` 을 도보(한 프레임 두 번, 사격마다 한 번), 차량, 비행, 헬기, 포탄, 원격 포탄, 조준선 미리보기가 모두 `buildings.some` 으로 불러 건물과 구조물 1000여 개를 매번 전부 훑었다. 호출마다 객체 둘과 축 배열을 새로 만들었다.

## F. 1인칭 실내와 계기판

- 계기 하나가 원판, 베젤, 눈금 12개, 바늘, 허브로 mesh 16개다. 계기가 많은 기종은 실내만 draw call 이 수십에서 백을 넘는다.
- 실내 재질 조합이 처음 그려질 때 셰이더 80개가 link 된다(B 항목).
- 계기 판독값이 React 상태로 들어와 계기판 전체가 0.15초마다 재조정된다.

## G. 도보

- 위의 A, B, C, D, E 가 모두 겹친다. 지상 시점 GPU 비용, 첫 사격과 손전등의 셰이더 컴파일, 0.12초마다 도는 도시 재조정, 프레임마다 차량 전체 재계산 두 번, 건물 전체 훑기 두 번이다.
- 총 모델 하나가 draw call 59개다.
- 무기는 주먹, 권총, 기관총, 저격총 넷이다. 산탄총이 없다.

## H. 그 밖에 확인한 것

- 기존 단위 테스트 중 `tier-buildings.test.mjs` 의 부품 예산 테스트(bronze 0 high 260 parts) 는 이번 작업 전부터 실패했다. 이번 작업 범위 밖이다.
- `WorldScene.jsx` 의 lint 오류 3개(`useResources` 의 immutability, `City` 의 쓰지 않는 인자 둘) 도 작업 전부터 있었다.
- 표본 6초는 주행 끊김을 놓친다. 해상도 자동 조절이 4초를 워밍업으로 쓰므로 6초 표본은 정책이 거의 작동하지 않은 구간만 잰다. 같은 빌드가 20초 표본에서는 p95 173ms, 긴 프레임 144회로 전혀 다른 숫자를 냈다. 주행은 20초 이상으로 재야 한다.
- 절대 숫자는 기계 상태에 세 배까지 흔들린다. 데스크톱 Chrome, gitkraken, postgres, docker 가 같이 도는 동안(load average 4) 재면 같은 빌드가 71fps 대신 25fps 로 나온다. `foreignGpuPct` 는 GPU 경쟁만 잡고 CPU 경쟁은 못 잡는다. 번갈아 재는 방식만 믿는다.
